anker-haike：
从客户原话到安全建单

OntoCare 已经告诉我们：型号和保修状态决定「哪些动作可能合理」。但客户会改口，工具会超时，按钮会被重复点击。一个合理的候选方案，为什么仍然不能直接执行？

本课唯一目标：沿着事实 → 会话状态 → 授权 → 执行这条链，指出每一层阻止了什么错误，并能自己判断一次提交是否应放行。

1. 一个客户在三轮中改变诉求

下面是教学场景，不是从项目日志中复制的真实工单：

TURN 01

客户：「S1 Pro 的右边不工作，左边正常。我已经清理过滚刷，没有冒烟。我想换货。」

TURN 02

客户：「等一下，不要换货，我是想退款。」

TURN 03

客户：按下提交后网络超时，于是再次点击。

如果用一个模型 Prompt 包办所有步骤，常见错误是：① 丢失「左边正常」和「没有冒烟」里的否定/对象；② 按已经过时的换货方案提交；③ 网络超时后重复创建服务单。

本课的设计答案：事实不能只靠对话摘要，状态不能只放在模型上下文，敏感写入不能只靠模型点头，失败重试不能只靠「再试一次」。

2. 事实账本：记录来源、极性和版本

源码阅读路径：interpret.py · FactCandidate 定义模型可提出什么事实；reduce.py · reduce_turn() 决定哪些事实有原话支持，如何写入与更正。

class FactCandidate(BaseModel):
    kind: Literal["symptom", "observation", "preference", "context", "action_taken"]
    value: str
    quote: str  # 本轮客户原话，不能引用助手建议
    subject: str | None = None
    polarity: Literal["affirmed", "negated", "uncertain"] = "affirmed"

# reduce_turn() 的关键验证
if not quoted(candidate.quote, text):
    continue

对于 TURN 01，可以理解为以下概念记录。这些是帮助理解的数据示意，并非模型运行实录：

原话与主体类型极性/含义
「右边不工作」subject = 右侧symptomaffirmed · 当前故障
「左边正常」subject = 左侧observationaffirmed · 正常观察
「已经清理过滚刷」subject = 滚刷action_takenaffirmed · 已做步骤
「没有冒烟」subject = 设备symptom 或其他事实类型，视抽取结果negated · 不能当作「正在冒烟」

代码中保存的事实还有 source_entry_ids、quote、revision、status 和 supersedes。当客户明确纠正原话时，旧事实会被标记为 superseded 或 retracted，而不是被无声覆盖。见更正与新事实写入。

本体论连接点：本体定义 Issue、Fact、Product 是什么、如何关联；事实账本记录「这个具体 Issue 中，有谁在何时说了哪句话」。本体是类型和关系，事实账本是有出处、可演进的实例数据。

3. LangGraph：运行步骤，而不是定义业务世界

在 sessions/graph.py · build_graph() 中，能看到真实的 StateGraph(SessionState)、add_node、add_conditional_edges 和 compile(checkpointer=...)。

一个非常容易记错的点：源码第一行文档注明「每轮从 START 到 END；卡片等待保存在问题状态中，不依赖跨轮图中断」。因此客户下一轮回复时，服务端根据已经保存的 pending_card、issues、stage 和版本继续处理。

如果客户在 TURN 02 改口，系统不能把旧卡片或候选方案视作永久有效。reduce.py 甚至会在某些事实依据变化时撤销现有待答卡片，防止基于旧前提继续推进。

4. 授权闸门：五个条件必须全部通过

haike 的 AuthorizationGate.check() 不只接收「模型认为可以」，而是逐项核验：

检查实际保护的边界
eligibility换货/退款须确认在保；物流类动作须满足对应物流条件
evidence换货/退款必须提供订单/凭证、地址、故障照片/视频、SN，且客户确认
safety存在未解除的 R4 设备安全风险或禁止操作时不提交
idempotency案件处于可提交状态，且相同动作未在运行或已经成功
review独立核对客户诉求、故障及产品；有冲突则不放行

review.py 为换货/退款准备独立审查：messages(case) 只把客户原话和订单商品行发给审查模型，而不把主流程判断的结论灌进去。审查输出再与候选方案比对，并核验引用片段是否真出现在原话中。

精确边界：独立审查并非在任何运行模式下都启用。源码在 LLM 全局关闭或已获人工批准时有特定放行分支；规则闸门的其他检查仍在。其作用是降低错误风险，不是数学意义的零错误保证。

6. 幂等：防止「请求成功了，但回答丢了」

在 executor.py 中，每次执行带 idempotency_key；store.py 会拒绝用相同幂等键发送不同请求。

# executor.py 中 _create_once() 的关键流程（节选）
if attempt > 1:
    found = await self.backend.find_service_order(client_ref)
    if found:
        return found
return await self.backend.create_service_order(
    ServiceOrderRequest(**params, client_ref=client_ref)
)

含义：上次超时也许只是响应没送达，不能立即再创建一次。先按请求标识查询已经存在的服务单；如果结果无法核实，源码会走人工核查路径。

不要过度承诺：这不等于任何系统都能保证 exactly-once。效果还取决于外部售后后端是否支持可靠的请求标识、幂等与查询。仓库也明确承认跨会话同订单去重仍有边界。

7. 和上一课的本体论怎么连接？

OntoCare

关系与规则：Product 对应什么 PN？知识是否属于该型号？在当前保修、经销商和排障状态下，允许准备什么动作？

haike

状态与执行：事实有没有原话支持？旧信息是否被更正？用户现在要退款还是换货？是否已确认材料？重复提交是否安全？

真正可复用的设计原则：把「领域关系」、「有出处的事实」、「流程状态」、「动作策略」、「真正的执行」设计成相互连接但权责清晰的层，不让一个 LLM Prompt 同时承担全部责任。

主动回忆 · 用你自己的话解释

请回答：「为什么在 OntoCare 中 allowed_actions() 给出候选动作之后，仍然需要 haike 风格的 AuthorizationGate？」试着用一个用户改口或重复提交的例子。

候选动作只是满足部分业务状态的决策，它可能随客户新消息、证据变化而过时。真正执行前必须重新核对当前事实、用户确认、资料、安全限制、独立审查、案件状态和幂等记录。这样系统不会把过时的建议直接变成有副作用的操作。
