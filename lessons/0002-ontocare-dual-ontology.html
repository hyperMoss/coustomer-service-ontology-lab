OntoCare 的双本体：
从「知道什么」到「允许做什么」

上一课我们知道：型号未确认，不能跨产品推荐排障步骤。这一课更进一步：如果型号、订单、渠道和排障状态全部变化，系统应该如何选择合法的下一步？

本课收获：能画出一个最小 Service Ontology；能读懂 allowed_actions 的条件分支；知道 OntoCare 与 haike 的职责差异。

1. 本体的两个问题

Service Ontology

描述业务世界：哪些实体存在、它们如何关联、数据来自哪里。

Product → OrderItem → Order
Knowledge → appliesTo → PN

Decision Ontology

定义合法动作空间：事实满足某些条件时，哪些行为可以建议或提交。

Warranty=UNKNOWN → request_proof
ReviewReady → prepare_review

这两个名字是该项目的工程术语。在实现中，前者主要通过 JSON/Python 实体关联，后者主要通过 allowed_actions() 的显式条件表达；它们不是两个独立运行的 OWL 推理引擎。

2. Service Ontology：关系比字段更重要

从真实文件 dataset.py 开始：它读取源表，整理 Products、Orders、Knowledge、Dealers、Tickets。一个订单可能有多条商品明细，不能只拿订单号当作某个产品的唯一标识。

看 app.py: resolve_product()：用户若只说 S1 Pro，可能得到 CONFLICTED；明确提到「滚刷」会指向扫地机候选，但返回的 PROBABLE 仍不等于核实了购买归属。

# 摘录：产品实体歧义，不能凭名字认定
if any(w in t for w in ROBOT_WORDS):
    ...
    return {"product": p, "evidence": "semantic=robot_vacuum",
            "state": "PROBABLE"}
return {"product": None, "evidence": "ambiguous_S1Pro",
        "state": "CONFLICTED"}

在 qa_workflows.py，只有 Published、Visible 的知识进入候选，而且检索时再按 PN 限定：

SOURCES = {source_id(r): r for r in RAW
           if r['Status'] == 'Published'
           and r['Consumer Visible'] == 'Visible'}

for sid, row in SOURCES.items():
    if pn not in row['PN'].split(';'):
        continue
核心理解：资料和客户提问的文字相似，不意味着资料适用于该订单商品。约束检索范围来自产品关系，而不只是提示词写着「不要幻觉」。

3. Decision Ontology：一组可解释的确定性规则

app.py 的 allowed_actions(case) 是本课最关键的函数。它读取四类信息：

prod = case.get("product")
warranty = case.get("warranty", "UNKNOWN")
dealer = case.get("dealer", "UNKNOWN")
ts = case.get("troubleshooting", "NOT_STARTED")

# 无产品：只能澄清；无有效质保信息：不能认定过保
# 在保 + 已授权 + 排障 FAILED：仅准备换货人工审核材料

4. 对照 haike：本体之外，还要有执行闸门

OntoCare 的 allowed_actions() 是「可做什么」的规则层。haike/actions/gate.py 则进一步处理「提交服务单之前要核对哪些不可省略的条件」：

为什么需要两层？规则可以告诉你「允许准备审核」，但实际执行属于有副作用的业务动作，必须进一步检查具体证据、用户确认、重复提交和权限。即便模型认为应该退款，也不等于程序允许退款。

5. 三道理解检查

练习 1 · 语义关系

客户明确了 T2080，搜索到了 T8D04 的高相似度知识条目。正确处理是？

练习 2 · 保修未知

产品已确认，客户希望换货，但订单和保修状态未知。应优先做什么？

练习 3 · 细微但关键的状态区别

客户说「还是不行」，系统记录 USER_REPORTED_FAILED。仅凭这一点可以准备换货审核吗？

主动回忆 · 不看源码回答

为什么 Order 和 OrderItem 要分开？为什么 prepare_replacement_review 与 direct_refund 要分开？

一个订单可能包含多件不同商品，每个商品行具有不同 SKU、型号或质保条件；只根据订单号无法确定哪件商品需要售后。准备换货审核是生成待审材料，直接退款是会改变真实财务/履约状态的敏感执行动作，后者需要额外授权且演示项目并未实现执行器。
